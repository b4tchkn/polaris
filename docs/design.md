# ゴール駆動・人間介在型 AI 作業環境 設計メモ

> 2026-10-05 版。初版メモを4視点（0→1プロダクト / 人間の理解 / 実現可能性 / 既存手法）で悲観レビューし、書き直したもの。

## 0. 目的

0→1 で新しく何かを作り出すとき（新しいアプリ、将来は事業なども）にも、1→100 で既にあるものを運用するときにも使える作業環境を作る。AI（Claude Code）が GOAL に向かって自律的に作業し、人間は**要所で理解しながら介在する**。

```
GOAL ◀── サブゴール ◀── サブゴール ◀── サブゴール
          (Loop)       (Loop)       (Loop)
```

- AI が自律的にサブゴールを立て、GOAL に向かって作業する。セクション4 の条件のときだけ人間が介入する（Human-on-the-loop）。
- 各 Loop の最後に、サブゴールを達成したかと、Loop の進め方を振り返る（ハーネスエンジニアリング）。
- GOAL は一度設定したあとも再設定できる。サブゴールは振り返りの結果で増えたり減ったりする。

- 人間が見るのはコードの細部ではない。「何が出来上がったか」と「本当にそれでいいか」を見る。
- 人間は毎ステップ承認する係にはならない。ただし、方向を決める瞬間には必ず関わる。

## 1. 初版からの主な変更（レビュー結果）

| 初版 | 変更後 | 理由 |
|---|---|---|
| PR のマージが承認ゲート | **サブゴールが承認ゲート**。PR は CI が通れば自動 | PR 単位だと、中身を見ずに押すだけになる |
| 判断材料は PR の解説、ADR、日次まとめ | **デモ**（触れるビルド、実機の録画）＋サブゴール完了報告 | 文章の要約は読まれなくなり、理解したつもりになるだけ |
| 最初に契約を書き、都度確認しない | 契約は**書き換えてよい仮説**。ゲートごとに見直す | 0→1 の完了条件は、作ってみて初めて書ける |
| 割り込みは AI の自己申告（迷い、自信のなさ） | **機械的なトリガー**で止める | AI は自信のある誤りに気づけない |
| 介入率を KPI にする | 「後から判明した手戻り」と「ゲートでの却下率」を見る | Goodhart の法則。エスカレーションを避ける方向に最適化される |
| 題材は既存の業務アプリ | 対象は 0→1 と 1→100 の両方。**最初の題材は小さな新規アプリ** | 既存アプリでは 0→1 の難所が検証されない |
| 骨格をすべて自作し、Phase 4 で plugin 化 | 骨格は既存手法を借りる。**自作は「理解・介在」の層に絞る** | 骨格はほぼ再発明になる |

## 2. 構成

エンジン（全プロジェクト共通）と状態（プロジェクトごと）を分ける。

```
.claude/                  エンジン
  skills/gdd-*/           init、Loop を1周回す、サブゴール完了報告、振り返り
                          1回の起動で1サブゴール進め、報告して止まる
  settings.json           環境全体の制約（permissions でハーネスとして強制する）
gdd/                      状態
  goal.md                 GOAL だけを書く：北極星のゴール、受け入れシナリオ、前提
  subgoals.md             サブゴールの一覧（次の1つは詳細、それ以降は粗く）
                          ※ goal.md / subgoals.md は AI が案を書けるが、書き込みには
                            毎回人間の承認が要る（permissions の ask で強制）
  state.md                AI が毎周、1ページ以内に書き直す
                          現状、出来たもの、判断ログの要点、却下された案（再提案を防ぐ）、
                          学び（振り返りの結果）
  reports/M<N>.md         サブゴール完了報告（AI が書き、末尾の「判断」欄に人間が書く）
  archive/                完了した GOAL
docs/design.md            この設計
```

### 配布方法

| 使い方 | 導入方法 |
|---|---|
| 新規リポジトリ（0→1：サービス開発、事業の立ち上げ） | Template Repository から作り、`gdd-init` で状態を空にする |
| 既存リポジトリ（1→100：既存の OSS など） | エンジンを Claude Code の plugin として入れ、`gdd-init` で `gdd/` を生成する |

このリポジトリ自身も `gdd/` に「基盤を作る」GOAL を入れ、ドッグフーディングで進める。

## 3. サブゴールの定義

サブゴールは、**大ゴールを分解した段階的なゴール**とする。大ゴールは `goal.md` の北極星で、サブゴールはそれに近づくためのゴールである。一覧は `subgoals.md` に置く。

各サブゴールには次の3つを書く。

| 項目 | 内容 |
|---|---|
| ゴール | このサブゴールで達成すること（1文） |
| 種類と完了条件 | **決める系**：仕様、方式、範囲などを人間と合意したら完了。成果物は仕様書、モック、比較表など<br>**作る系**：受け入れシナリオが通ったら完了。成果物は動くもの |
| 見せるもの | ゲートで人間が判断に使う成果物（デモ、モック、仕様1枚） |

どちらの種類でも、最後は人間のゲートで「次へ進む / 方向転換 / やめる」を判断して締める。外れたら、作ったものを捨てて方向転換する前提で進める。

1. **ゴールは1つにする**：見せるものが出せない区切りは、粒度が誤っている。
2. **大きさは、外れたら丸ごと捨てても惜しくない量を上限にする**
3. **大きさは不確実性に合わせて変える**：初期は小さく、方向が固まったら大きくする。却下が続いたら小さく、承認が続いたら大きくする。頻度は人間の都合（例：1日1回なら見られる）から逆算する。
4. **詳しく決めるのは次の1つだけ**：その先は粗い見通しにとどめ、ゲートごとに見直す。

0→1 アプリでの典型的な並び：

| # | ゴール | 種類 | 見せるもの |
|---|---|---|---|
| M0 | 誰の何を解決するかを決める | 決める | 課題、ペルソナ、コア体験を1枚で |
| M1 | コア体験の画面仕様を決める | 決める | クリックできるモック（データなし） |
| M2 | 技術構成とデータモデルを決める | 決める | 構成図と比較案を1枚で |
| M3 | コア体験1本を端から端まで動かす | 作る | walking skeleton のデモ |
| M4〜 | ユーザーストーリーを1つずつ実現する | 作る | ストーリーごとのデモ |

役割分担：AI が次のサブゴール（ゴール / 種類と完了条件 / 見せるもの）を提案し、人間が承認するか直す。

## 4. 人間が介入する条件（Human-on-the-loop）

基本は AI が自律的に進める。人間が介入するのは次の4つのときだけ。

| # | 条件 | 動き |
|---|---|---|
| 1 | GOAL / サブゴールの設定を最終決定するとき | AI が案を出し、人間が確定する（`goal.md` / `subgoals.md` への書き込みは ask で必ず承認） |
| 2 | 判断結果が GOAL / サブゴールの達成に影響するとき | 止まって人間を待つ。AI の自己申告だけに頼らず、セクション7 の機械的なトリガーと併用する |
| 3 | AI が GOAL / サブゴールを達成したと判断し、成果物をレビューするとき | Loop の最後のゲート（サブゴール完了報告＋デモ） |
| 4 | Loop のレトロスペクティブをするとき | 3 と同じゲートでまとめて行う |

これ以外（作業の進め方、サブゴールの中での細かい判断など）は AI に任せ、結果をサブゴール完了報告に載せる。

## 4.1 サブゴール完了報告（1枚だけ）

- 何が出来たか、どう触るか（デモのリンク、録画）
- 一番自信がない判断
- 捨てた案と、その理由
- 人間への質問
- 振り返り（セクション5）
- 次のサブゴールの提案（振り返りを反映したもの）

報告が読まれなければ、次の周には進まない。

## 5. 振り返り（レトロスペクティブ）

ゲートのたびに振り返り、その結果を次のループに反映する。

| 項目 | 内容 |
|---|---|
| 続けること | うまくいった進め方 |
| 問題 | 手戻り、人間が介入した箇所、ゲートで却下された理由 |
| 変えること | 1項目ごとに**反映先**を必ず書く |

「変えること」の反映先は次の4つ。反映先がない項目は書かない。

| 反映先 | 例 |
|---|---|
| `subgoals.md`（人間が承認） | サブゴールの追加・削除・並べ替え、粒度の変更、見せるものの変更 |
| `goal.md`（人間が承認） | GOAL の再設定、受け入れシナリオ、前提の修正 |
| `state.md` の「学び」欄 | 次のループで AI が守ること（却下された案、確定した方針） |
| ハーネス | ルール、hook、テストの追加（`harness-regression-guard`） |

振り返りには2つのレベルがある。

- **サブゴールの振り返り**：軽く行い、サブゴール完了報告に含める。
- **大ゴールの振り返り**：重く行い、ゴール全体の手戻りと介入をまとめる。ハーネスの修正は主にここで行う。

AI が案を出し、人間が承認または修正する。

## 6. 大ゴールの切り替え

```
最後のサブゴールのゲート
   ▼
① 大ゴールの完了ゲート（人間）
   AI の完了報告：受け入れシナリオと結果の対応、デモ、大ゴールの振り返り、
   やり残し、次のゴール候補 2〜3案
   人間が判断する：完了 / 追加のサブゴールで続ける / 終了
   ▼
② アーカイブ：gdd/archive/NN-<slug>/ に goal.md / subgoals.md / state.md / 完了報告を移し、
   gdd-init で空の状態ファイルを作り直す
   ▼
③ 新しい大ゴールの設定（人間）
   AI が「引き継ぐ前提」の案を出す（確定した仕様、技術構成、既存の成果物、振り返りの学び）
   人間が承認・修正し、gdd-init が作った goal.md に書く
   ▼
④ 新しいゴールの M0 から再開
```

- 2つ目以降のゴールの M0 は、「何を変える / 何を足すか」を決めることから始める。前提が引き継がれているため、「誰の何を解決するか」から決め直さない。
- 引き継ぐものは `goal.md` の「前提」欄に書く。新しいファイルは作らない。
- GOAL は完了前でも再設定できる（セクション4 の条件1）。その場合も同じ流れで、`subgoals.md` を作り直す。
- 過去のゴールは `gdd/archive/` に残す。AI は普段は読まず、必要なときだけ参照する。

## 7. 途中で止まる条件（機械的に判定する）

- 戻しにくい判断：データモデル、外部サービスの選定、課金、認証、依存の追加
- N 周続けて `state.md` に実質的な変化がない
- 受け入れシナリオやテストを緩める変更があった

## 8. 検証

- 受け入れシナリオは人間が確定する。AI は人間の承認なしに書き換えられない（ask）。
- AI の自己採点は甘くなるので、評価は別の役（evaluator）か E2E で行う。

## 10. 進め方

- **Phase 1**：`goal.md` と `state.md` のテンプレートを作り、1サブゴールを進める skill を1本作る。小さな新規アプリで手動で3周ほど回し、サブゴールの粒度と報告の形を固める。
- **後回し**（Phase 1 を回してから判断する）：自動起動、リスク別ゲート、指標の計測、plugin 化、ソフトウェア以外への適用。

## 11. 残すもの（初版から）

- 判断軸は「元に戻せるか」
- ガードレールはプロンプトではなくハーネス（sandbox、permissions、hooks、CI）で強制する
- 人間の介入をルール、テスト、hook の修正に変換する（`harness-regression-guard`）
