# polaris 改修計画

> 2026-10-10 版。SDD（Spec Kit）・スクラムガイドとの比較と、現状の問題の洗い出しから合意した方針と計画。2026-10-10 に実装した（ブランチ `feat/redesign`）。計画から変えた点は末尾の「11. 実装で決めたこと」。

## 1. 目的

GDD（Goal Driven Development）を次の形で成り立たせる。

- 細かい仕様を先に決めず、ループを回しながら不確実なことを確かめ、ゴールに近づく。
- 人間は方向を決める場面でだけ関わり、それ以外は AI が自律的に進める。
- 依存しない作業は並列に進める。

## 2. 背景

### Spec Kit との違い

Spec Kit（github/spec-kit）は機能単位で spec → plan → tasks → implement を進め、`/speckit.converge` で仕様と実装の差を埋める。人間のレビュー関門、仕様の書き換え（flow-back / living spec）、拡張 hook も持つ。polaris との差は次のとおり。

- 単位：Spec Kit は1機能を作り切る。polaris は GOAL → サブゴール1つ → 止まる。
- 人間が見るもの：Spec Kit は文書と差分。polaris はデモと短いレビュー。
- 強制：Spec Kit の hook は LLM が yml を読んで実行する。polaris は Claude Code の hook と permissions で強制する。
- 評価：polaris は別コンテキストの evaluator が採点する。
- 改善：polaris は振り返りで改善を提案し、学びを hook や設定に変える。判断理由を `adr.md` に残す。

### スクラムガイドとの関係

polaris はスクラムではない（一部だけの導入はスクラムと呼ばない、スクラムガイド「最後に」）。スクラム化を検討した結果、「人間が並べたバックログを上から消化する」形は GDD の「AI が自律的にサブゴールを立てる」（design.md 0）と合わないと判断した。スクラムから借りるのは振り返りの型と完成の定義だけにする。

## 3. 現状の問題

- ゴールに向かっているかを測っていない。受け入れシナリオの状態はゴールの最後に1回見るだけで、未確定事項の一覧もない。
- 人間への確認が多い。1周で最大4回聞く。次のサブゴールの3案は `adr.md` 19件中11件を占め、ほぼ毎回「順番どおり」が選ばれていた。
- 直列でしか進められない。次のサブゴールは1つしか置けず、状態ファイルが共有のため並列にするとコンフリクトする。
- ループの手順が複雑になってきた（手順2の判断テーブル、改善案の4種類、`state.md` の判断ログの重複）。
- AI に任せてよいかを判断する材料（事前の基準、実績の記録）がない。
- 自分自身（このリポジトリ）の整備に偏っており、実アプリでの検証が少ない。

## 4. 方針

- 次に何をやるかは AI が決める。基準は「ゴールに一番近づくもの、一番大きな不確実性を潰すもの」。人間が並べた順に消化する方式にはしない。
- ゴールの設定を一番重視する。ゴールが後のすべての判断の基準になるため、別コンテキストのサブエージェントで審査する。
- 機械的に確かめられる判断は、AI の処理から frontmatter とスクリプトに移す。
- 任せる範囲は、事前のハーネスと実績の両方で決める。
  - 事前：受け入れシナリオを実行できる確かめ方にする、選択を別コンテキストで審査する、影響の大きさで線を引く、最初に人間の判断基準を聞く。
  - 実績：人間が覆したか、後から手戻りが出たか。
- 学習はモデルではなくファイル（学び、判断、覆した記録）に溜まる。効くのはそのリポジトリの中だけで、全ユーザーに効かせるには plugin の手順や雛形に移す。
- 方向の判断（決める系のサブゴール、ゴールの変更）と戻しにくい行為（停止条件）は、自律度に関係なく人間に聞く。
- 「コミットしない」ルールはやめる。サブゴールごとにブランチを切り、サブゴールの完了時に PR を作る。
- 仕組みは増やすより削る。変更は小さく、段階ごとに eval を通す。

## 5. AI の処理から機械的な処理に移すもの

frontmatter に情報を持たせ、`plugins/polaris/scripts/gdd-status.sh` が読んで判定する。hook と同じく bash だけで動かすため（jq に依存しない）、frontmatter は1行1項目の平らな形にする。

| 今 AI がやっている判断 | 機械化した後 |
|---|---|
| サブゴールの状態 | 置いているディレクトリ（candidates / in-progress / done） |
| 決める系は人間に聞く | `type: decide` なら必ず止まる |
| 評価基準が定量か定性か | 基準ごとの `kind`。定性が1つでもあれば人間に聞く |
| 定量的な評価基準の採点 | 基準ごとの `check`（コマンド）をスクリプトが実行。残りは evaluator |
| 受け入れシナリオの状態 | `goal.md` のシナリオごとの `check` をスクリプトが実行 |
| 完成の定義の確認 | `goal.md` の `done_checks` をスクリプトが実行 |
| ゴールにつながっているか | サブゴールの `advances`。空なら hook が書き込みを拒否 |
| 並列にしてよいか | `depends_on` が全部 done にあり、`touches` が in-progress の他と重ならない |
| 停滞 | 直近 N 件のレビューのシナリオ状態と未確定事項を比べる |
| 影響の大きさ | `git diff --stat` を `goal.md` の上限と比べる |
| 聞かずに進めてよいか | 上の結果と、レビューの `overridden` / `rework` から決める |
| 理由を聞くか | 人間が覆したとき（`overridden: true`）だけ |

AI に残るもの：候補から次のサブゴールを選ぶ、完了条件と評価基準を書く、定性的な判断の材料作り、振り返り、リファインメント、各審査サブエージェントの判断。

frontmatter の例：

```yaml
# gdd/goal.md
scenario_1_check: npm run e2e -- signup
scenario_2_check: human
done_checks: npm test && npm run lint
uncertainty_1: 決済は Stripe で足りるか | open
max_files: 10
max_lines: 300
prefer: certainty
```

```yaml
# gdd/subgoals/candidates/signup-form.md
type: build
advances: scenario_1, uncertainty_1
depends_on: []
touches: src/signup/
criterion_1: 入力検証が動く | quantitative | npm test -- signup
criterion_2: 迷わず登録できる | qualitative
```

```yaml
# gdd/reviews/signup-form.md
scenario_1: partial
scenario_2: not-started
auto: false
overridden: false
rework: false
```

## 6. 並列化と PR

- メインのセッションが `gdd-status.sh` で並列にできる候補を出し、worktree を分けたバックグラウンドのサブエージェントに割り振る。
- サブゴールごとにブランチ（worktree）を切り、作業中は適宜コミットする。
- サブゴールが完了したら、種類によらず PR を作る（コード、サブゴールのファイル、レビュー、ADR を入れる）。push と PR のマージは ask ルールで人間が承認する。CI が通ったらマージする。
- done は「マージ済み」とする。依存するサブゴールは、依存先がマージされてから着手する。
- サブエージェントは AskUserQuestion を使えない。判断が必要になったら止まってメインに返し、メインが人間に聞いて `SendMessage` で再開させる。
- 共有ファイル（`state.md`、done への移動、候補の追加）はメインだけが更新する。
- 複数の人が別々に作業する場合は、各自のクローンか worktree で行う。サブゴールの1件1ファイル化でコンフリクトを避ける。

### 確認済みの事実（公式ドキュメント、2026-10-10）

- サブエージェントの hook 入力には親と同じ `session_id` と `agent_id` が入る。今の hook は控えを `session_id` だけで分けているため、並列だと上書きし合う。
- worktree に入っても `CLAUDE_PROJECT_DIR` はセッション開始時の場所（メインのチェックアウト）のまま。作業中の場所は入力の `cwd`。今の hook は worktree 内の `gdd/` を監視できていない。
- サブエージェントの worktree は既定でリモートの既定ブランチから分岐する。`worktree.baseRef: "head"` でローカルの HEAD（コミット済みのもの）から分岐する。
- バックグラウンドのサブエージェントの許可プロンプトはメインに出る。ask ルールは並列でも効く。
- サブエージェントは `Skill`、`Agent`（3階層まで）、`SendMessage` を使える。`AskUserQuestion` は使えない。
- project スコープの plugin は worktree でも読み込まれる。

## 7. 段階ごとの計画

### 段階1：土台

- `gdd-loop` の SKILL.md を骨格だけにし、各手順の詳細を補助ファイルに分ける。
- サブゴールを1件1ファイルにする：`gdd/subgoals/{candidates,in-progress,done}/<slug>.md`。ファイル名は slug、並び順は持たない。
- `gdd-status.sh` を作る。
- hook を直す：控えを `session_id` と `agent_id` の組で分ける、基準を `cwd` の git ルートにする、監視対象を `subgoals/**` にする。
- 合わせて直すもの：`gdd-init`、雛形、このリポジトリ自身の `gdd/` の移行。
- 完了条件：既存の eval と hook のテストが通る。

### 段階2：ゴール設定のハーネス

- ゴールを決めるときに人間に2〜3問聞く（優先すること、触ってほしくない領域）。答えは `goal.md` に書く。
- `goal.md` の frontmatter：シナリオごとの `check`、`done_checks`、未確定事項、影響の大きさの上限。
- ゴール審査サブエージェント（`agents/goal-reviewer.md`）
  - 起動：`goal.md` の案を書いたあと、人間が承認する前。ゴールを変更するときも。
  - 見るもの：北極星が1文で言えるか、各シナリオに確かめ方があるか、evaluator が測れるか、完成の定義、未確定事項、人間の判断基準との矛盾、ゴールの大きさ。
  - 返すもの：項目ごとに「OK / 問題（理由）」の表。人間は承認するときにこれも見る。
- 完了条件：良いゴールと悪いゴールの両方で eval が通る。

### 段階3：ゴールまでの距離を測る

- `gdd-status.sh` がシナリオの `check` と `done_checks` を実行する。自動化できないものは evaluator が見る。
- 停滞の判定もスクリプトで行う。
- サブゴールの `advances` 必須を hook で強制する。
- 完了条件：各挙動の eval が通る。

### 段階4：ループの単純化

- ループは計画 → 作業 → レビュー → 振り返り。
- 人間への質問は1問だけ：「OK（次は X、理由 Y）/ 変える / やめる」。この段階では毎回聞く。割り込みや方向転換は「変える」で扱う。
- 削除するもの：次のサブゴールの3案、手順2の判断テーブル、`state.md` の判断ログ。改善案の種類は2つ（学び / 候補）にする。
- 完了条件：書き換えた eval が通る。

### 段階5：任せる仕組み

- 選択の審査サブエージェント：`goal.md`、未確定事項、`adr.md` を渡し、AI の選んだサブゴールがゴールにつながるか、過去の判断と矛盾しないかを見る。
- 影響の大きさの判定と、`overridden` / `rework` の記録はスクリプトで行う。
- 聞かずに進むのは次の全部がそろったときだけ：決める系ではない、定性的な基準がない、審査で異議がない、影響が範囲内、直近で覆されていない、手戻りがない。
- 完了条件：聞かずに進む場合と止まる場合の両方の eval が通る。

### 段階6：並列化と PR

- 6 の内容を実装する。「コミットしない」ルールを外し、`worktree.baseRef: "head"` を `gdd-init` で設定する。
- 完了条件：並列の eval が通り、hook が並列と worktree でも正しく動く。

### 段階7：説明の更新

- README と `docs/design.md` を新しい流れに合わせる。

## 8. 変えないもの

- 戻しにくい行為を ask ルールと hook で止める仕組み。
- evaluator を別のコンテキストで動かす（自己採点しない）。
- 学びは消さない（仕組みに移したものは整理して別の場所に移す）。

## 9. 保留

- 任せる範囲を人間が事前に宣言する（過去に却下済み。状況が変わったので段階5の後に見直す）。
- 自律で続けられる周回数の上限（過去に却下済み）。

## 10. 未決事項

- `subgoals/` への書き込みを ask で止め続けるか。
- `adr.md` で同時に追記したときのコンフリクトの扱い。
- 停滞とみなす N、影響の大きさの上限の既定値、聞かずに進むまでに必要な覆されない周の数。

## 11. 実装で決めたこと

- 未確定事項は `goal.md` ではなく `state.md` の「Uncertainties」に置く。`goal.md` は書くたびに人間の承認が要るため、毎周の状態更新に向かない。レビューの `progress:` に未解決の数を残し、停滞の判定に使う。
- `subgoals/` と `reviews/` への書き込みは allow にする。どのサブゴールも PR になり、人間は PR レビューで変更を見るため（人間の判断、2026-10-11）。hook は `advances:` の無いサブゴールのファイルを戻す。
- ADR は `gdd/adr/<日付>-<slug>.md` の1判断1ファイルにした。既存のファイルは変えられず（hook が戻す）、新しいファイルはどのセッションからでも足せる。
- 既定値：停滞 = 直近3件のレビューの progress が同じ。聞かずに進むには直近3件が覆されず手戻りも無いこと。大きさの上限は雛形で 10 ファイル / 300 行。
- 並列化は1セッション内で行う：worker サブエージェント（`isolation: worktree`）がブランチ `gdd/<slug>` で作ってコミットし、メインが統合する。`gdd-init` は `worktree.baseRef: "head"` を書く。
- ゴールまでの距離は worker の worktree で測る（`gdd-status.sh --at <worktree>`）。メインのチェックアウトにはマージ前の成果が無いため。
- 段階1〜6は1つのブランチで順にコミットした。この環境では eval を流せないため、段階ごとに eval で確かめる手順は、最後にまとめて人間が流す形にした。
