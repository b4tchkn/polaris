# gdd-loop

1回の起動でサブゴールを1つ進め、報告して止まる。commit はしない。

引数でディレクトリ（例：`simulations/morning-review`）を渡されたら、以下の `gdd/` はすべて `<ディレクトリ>/gdd/` と読み替え、作るものもそのディレクトリの中に置く。引数がなければリポジトリのルートを対象にする。

## 1. 状況を読む

- `gdd/goal.md` / `gdd/subgoals.md` / `gdd/state.md` を読む。
- `gdd/reports/` に報告があれば、一番新しいものを読む。過去の報告の「振り返り」と「改善の提案」にも目を通す（5 で使う）。

## 2. 前回の判断を確認する

前回の報告がなく、`goal.md` が雛形のまま（`<ゴール名>` が残っている）なら、サブゴールを進めずに次を行って止まる。

- AskUserQuestion で、大ゴールを決めるための質問をする（誰が使うか、何ができれば成功か、など）。選択肢とおすすめを付け、用語を使わない。
- 答えをもとに `goal.md` と、`subgoals.md` の SG0 と「その先」を書く（ask で承認が入る）。

前回の報告がなければ 3 に進む。あれば、末尾の「判断」欄を見る。

| 判断 | 動き |
|---|---|
| 空 | 6 の手順で人間に選んでもらい、判断欄に書いてから、この表をもう一度たどる |
| 次へ進む | 判断を `state.md` の判断ログに転記する。判断欄で採用された「改善の提案」を反映先に反映する（採用されていない提案は反映しない）。報告の「次のサブゴールの提案」で `subgoals.md` を更新し（前のサブゴールを「完了：」に移して結果を書く）、3 に進む |
| 方向転換 | 判断とコメントを `state.md` の判断ログに転記する。コメントを反映した `subgoals.md` の修正案を書いて止まる |
| やめる | 判断を `state.md` の判断ログに転記して止まる |

`subgoals.md` / `goal.md` への書き込みは ask で人間の承認が入る。断られたら止める。

人間の判断やコメントを反映するとき、解釈が分かれる点（数、範囲、どこに書くか）は、書く前に3案とトレードオフを出して選んでもらう。

## 3. サブゴールを進める

- `subgoals.md` の「次：」のサブゴールだけに取り組む。その先には手を出さない。
- `state.md` の「却下された案」は再提案しない。「学び」に従う。
- 案を出すときは3案にする（決める系の見せるもの、止まって聞く判断、5 の次のサブゴール）。3案は、選んだ結果で次の行動が変わるか、トレードオフ（速さ / 確実さ / 範囲など）が違うものにし、各案にトレードオフを1行で書く。言い換えだけの3案にしない。
- 外のデータ（API、ログ、チケットなど）を使う取り方や完了条件は、決める前に実データで試し、前提のデータが本当にあるか確かめる。
- 作る系の完了は、作ったものを本来の起動方法（skill なら `/<名前>`、アプリなら起動して触る）で確かめる。AI が会話の中で手順をなぞっただけでは完了にしない。AI が起動できないときは、人間に起動を頼む。
- 次のどれかに当たったら、そこで止まって人間に聞く（AskUserQuestion で3案から選んでもらい、6 と同じく理由も聞いて `gdd/adr.md` に残す）。
  - 戻しにくい判断：データモデル、外部サービスの選定、課金、認証、依存の追加
  - 受け入れシナリオやテストを緩める変更
  - 判断結果が GOAL / サブゴールの達成に影響する

## 4. state.md を書き直す

1ページ以内で全体を書き直す（追記しない）。現状 / 出来たもの / 判断ログ / 却下された案 / 学び。

- 学びは消さない。重複は統合してよい。
- ハーネスに移した学びは「→ ハーネス化済み：<場所>」を付けて残す。

## 5. サブゴール完了報告を書いて止まる

- `templates/report.md` の形で `gdd/reports/SG<N>.md` に書く（`<N>` は今回のサブゴールの番号）。
- 「評価基準での振り返り」では、サブゴールの評価基準（定量 / 定性）ごとに、結果と達成したかを書く。
- 振り返りは、今回の周だけでなく、`state.md` の学び全体と過去の報告も見て行う。
- 「改善の提案」に番号を振り、1項目ごとに反映先とトレードオフ（入れると何が良くなり、何が増えるか）を書く。反映先がない項目は書かない。種類は次の4つ。
  - 学びの追加：次のループで AI が守ること → `state.md` の学び
  - 仕組みの修正：GDD の進め方を直す → `gdd-loop` / `gdd-init` / 雛形 / `docs/design.md`
  - 学びのハーネス化：繰り返し出る学び、機械的に確かめられる学びを強制に変える → `.claude/settings.json` / hook / `CLAUDE.md`
  - サブゴールの見直し：「その先」の追加・削除・並べ替え → `subgoals.md` / `goal.md`
- 提案は書くだけにする。反映するのは、人間が判断欄で採用したものだけ（2 で行う）。
- 「次のサブゴールの提案」は3案出す（3 の案の出し方に従う）。各案に評価基準を書き、定量（数字で測る）か定性（人間が判断する）かを明記する。
- 「判断」欄は空のままにする（6 で埋める）。
- 同じ内容をチャットにも出して、6 に進む。

## 6. 判断を選んでもらって止まる

判断欄を埋めるよう頼むだけにしない。必ず AskUserQuestion で選択肢を出し、人間に選んでもらう。

- 聞き方は、人間がコードや用語を知らなくてもわかる言葉にする。何について聞いているのかを、質問文の中に書く。
  - 質問1（1つ選ぶ）：「SG<N> の出来上がりで OK か」。選択肢は「OK、次へ進む」「直したい（方向転換）」「やめる」。決める系なら「OK」を3案に分ける（例：「A 案で次へ進む」）。
  - 質問（1つ選ぶ）：「次のサブゴールをどれにするか」。3案を、トレードオフがわかる説明付きで出す。
  - 質問2（複数選べる）：「改善の提案のうち、どれを直すか」。提案ごとに、何が変わるかとトレードオフを1行で書く。提案がなければ聞かない。
- おすすめの選択肢を先頭に置き、「(Recommended)」を付ける。
- 答えを判断欄に書く（例：`次へ進む。採用 1, 2（AskUserQuestion で選択）`）。「直したい」や Other を選んだ場合は、書かれた内容をコメントとして写す。
- 案から選んでもらったとき（見せるものの3案、次のサブゴールの3案、3 で止まって聞いた判断）は、続けて AskUserQuestion で「なぜそれにしたか」を聞く。選択肢は各案のトレードオフから作った理由2〜3個とし、Other で自由に書けるようにする。
- 答えを `gdd/adr.md` に1件追記する（無ければ作る。書き直さない）。項目は、日付とサブゴール / 何を決めたか / 出した案（トレードオフ付き） / 選んだ案 / 理由（人間の答えをそのまま写す）。
- 書いたら止まる。反映と次のサブゴールは、次の起動で 2 から行う。
