# サブゴール完了報告：SG3 小さな新規アプリの題材を決める

## 何が出来たか、どう触るか

- 題材の候補3案と比較（下の表）。選ぶ基準は次の3つ。
  - ペルソナがこの報告を読む人自身である：ユーザー調査をしなくても、ゲートで「本当にそれでいいか」を判断できる
  - 認証・課金・外部サービスなしでコア体験が成り立つ：戻しにくい判断で止まらずに 0→1 を回せる
  - design.md 3 の典型的な並び（題材決め → 画面仕様 → 技術構成 → walking skeleton → ストーリー）を一通り踏める大きさ
- デモ：この表。

| | A. 1on1 の話したいことメモ | B. 家の消耗品の在庫チェック | C. あとで読むの1日1本 |
|---|---|---|---|
| 課題 | 話したいことは思いついた時に浮かぶが、1on1 の直前には忘れている | 買い物中に「洗剤は家にあったか」がわからず、重複買いや買い忘れが起きる | 「あとで読む」が溜まり、結局読まない |
| ペルソナ | 週1で 1on1 がある会社員（自分） | 一人暮らしか、家の買い物を主に担当する人（自分） | 技術記事を日常的に保存するエンジニア（自分） |
| コア体験 | 思いついた時に3秒でメモ → 1on1 の直前に一覧を開き、話したら済にする | 使い切ったら1タップで「切れ」→ 買い物中に「切れ」の一覧を見る | 保存した中から、毎日1本だけ出てくる。読んだか、捨てるかを選ぶ |
| ストーリーの例 | 相手ごとに分ける / 次回に持ち越す / 過去の話題を振り返る | 品目の追加 / 「残り少ない」の段階 / 店ごとの並び | URL の保存 / 出す順の工夫 / 読んだ記録 |
| 懸念 | 小さすぎて、技術構成の判断が浅くなるかもしれない | 家族と共有したくなると、同期と認証が要る | URL からタイトルや本文を取るので、外部への通信が要る |

- おすすめは A。外部への依存がなく、使う場面（思いついた時 / 1on1 の直前）がはっきりしていて、デモで良し悪しを判断しやすい。

## 一番自信がない判断

- ペルソナを「報告を読む人自身」に絞ったこと。判断はしやすくなるが、自分以外のユーザーを想定する 0→1 の難しさ（ユーザーの理解）は検証できない。

## 捨てた案

- 業務アプリ（既存プロダクト関連など）：既存プロダクトの文脈が前提になり、0→1 の検証にならない。
- 複数人で使うアプリ（チームの当番表など）：最初から認証と共有が要り、戻しにくい判断が SG の早い段階に来る。
