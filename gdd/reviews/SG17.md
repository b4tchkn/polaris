# サブゴールレビュー：SG17 skill の挙動を `claude plugin eval` で確かめる

## 何が出来たか、どう触るか

- `plugins/polaris/evals/` に2ケース。各ケースは `prompt.md`（起動するコマンドと許可ツール）、`case.yaml`（`scaffold_script` が試験用 `gdd/` を作る）、`graders/*.md`（できたファイルとレビューの判断欄を見る）の3点
  - `auto-continue`：SG0（a.txt）・SG1（b.txt）が定量のみ、SG2（c.txt）が定性あり。graders：a.txt と b.txt が存在、SG0.md / SG1.md の判断欄に "Proceed (automatic)" がある、SG2.md には無い
  - `goal-reached`：SG0 のあと「その先」が空。graders：返答に「goal looks reached / completion report」がある、subgoals.md に SG1 が書かれていない
- 人間の指示で洗い出しを広げ、4ケース追加（計6ケース）
  - `init`：`/polaris:gdd-init` で雛形4ファイルができ、settings.json を書こうとする（eval では settings.json への書き込みが拒否されるため「試みた」までを見る）
  - `first-run`：goal.md が雛形のままなら、ゴールを決める質問を返し、勝手に goal.md を書かない（eval では AskUserQuestion が使えず文章で質問する）
  - `apply-proceed`：前回の判断「次へ進む」で、SG0 が Done に移り、選ばれた SG1 が Next になって進む
  - `apply-stop`：前回の判断「やめる」で、判断ログに書いて何も進めない
  - 既存2ケースに「evaluator が `polaris:evaluator` として呼ばれた回数」のグレーダー
- eval が見つけた plugin の抜け2つを直した：gdd-loop 手順2に完了セクションの形式（`## Done: SG<N> <goal>`、表を残し Result 行）、gdd-init 手順2に「Write ツールで書く（Bash のコピーは hook が戻す）」
- README に「Testing the skills」の節と実行コマンド
- `.gitignore` に `plugins/polaris/evals/results/`
- デモ：リポジトリのルートで下を実行。2ケースが pass すれば OK。各ケースが本物の Claude セッション1回なので数分とトークンを使う

```
claude plugin eval plugins/polaris --scaffold --allow-tools Bash Write Edit --ablation none --runs 1 --no-publish
```

## 一番自信がない判断

- グレーダーの書式（`type: regex` に `target: {source: file, path: ...}`、`match: not_contains`）は、公式ドキュメントのページが 404 で、CLI の説明と埋め込みリファレンスから組み立てた。読み込みは通ったが、採点が意図どおり効くかは実走で初めて分かる
- eval の中では AskUserQuestion に答える人間がいない。`goal-reached` は2択を聞いた時点で終わる想定で、返答の文面を正規表現で見ている

## 捨てた案

- `claude -p` を呼ぶシェルテスト：ask の通し方と結果の判定を自作することになる。公式の eval がある
- fixture をファイルとして置いて scaffold でコピーする：scaffold の実行場所からケースのディレクトリを指す方法が分からない。heredoc で自己完結させた
- LLM グレーダー（`type: llm`）：ファイルと判断欄を見れば決定的に判定できる
